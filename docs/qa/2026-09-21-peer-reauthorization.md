# 同 MAC 重新入网后的直连恢复（0.1.14）

## 现场与根因

同一设备退网重新加入时，协调服务按 MAC 复用 NodeID 和虚拟 IP，并为新私钥签发证书。现场设备的 MAC 与名称已成功更新，IP 保持 10.77.0.14；其他节点却在旧证书撤销后永久保留 `revoked` / `closed`，收到新证书对应的在线成员快照也不能重新协商。界面表现为协调服务器已连接、对端直连失败。

## 修复

- 串行处理成员变更的撤销、旧连接关闭和新授权恢复。
- 仅协调服务新发布的明确在线成员可以重新授权；缓存、缺席、离线成员不会撤销禁用状态。
- 先关闭旧连接、清除旧待处理握手和请求，再启用新的设备会话状态。
- 保留已使用的会话代次上限，拒绝旧授权重放；旧任务的迟到回调不影响新会话。
- 自动向所有在线对端发起协商，不要求发起用户流量，也不影响其他已建立的连接。
- 控制连接恢复时先发送历史撤销记录，再发布当前在线身份，避免旧通知覆盖新授权。
- TUN 投递检查原会话的取消状态并与成员更新同步；碎片按会话代次隔离，同时保留每设备及全局内存限额。
- 设备登记读取复用 Windows 文件共享冲突重试；登记文件暂时不可读时拒绝本次准入并允许自动重试，不再误判成永久身份不匹配。
- 定期登记检查每轮只读取一次完整快照，避免文件持续占用时按设备数量叠加重试等待、阻塞协调服务。

## 验证

修复前，新增成员恢复测试及四节点集成测试均失败：收到新在线成员后仍未授权，其他节点的会话持续为 `closed / peer_revoked`。修复后这些用例通过。

四节点测试使用真实协调服务、TLS/QUIC 和注册处理：同一 MAC 连续两次更换名称、重新注册并轮换证书，保留 NodeID、IP 和注册数量；等待旧证书被撤销后，只启动重入网的节点，其余三个节点自动恢复直连并能双向传输，同时无关连接的会话身份不变。

另外检查离线成员不能恢复授权、旧握手代次不能重放、旧任务回调不能损坏新握手，以及既有撤销状态发布和成员快照次序用例。

控制重连用例在修复前确认收到 online 快照后再收到旧 `disconnect_peer`，修正通知顺序后通过。延迟的旧会话投递会被拒绝，相同 packetID 的不同代次碎片不能混合重组。

20 节点并发入网回归发现偶发初次身份拒绝。增加 Windows 文件独占 50 ms 的确定性测试，确认原登记读取立即失败；复用现有共享冲突重试后通过。登记文件缺失、损坏和不可读仍拒绝准入，但客户端允许后续重试；真正的身份不匹配保持永久拒绝。修复后 20 节点无流量全互联测试连续 5 次通过。

## 使用与范围

发布验证：`go test ./... -count=1 -timeout=180s` 全部通过；登记扫描改为单快照后，对文件占用、登记不可用、重复身份、离线撤销、同 MAC 重入网和控制重接运行增量回归，全部通过；最终 `go vet ./...` 通过。

2026-09-21 16:50 发布至固定 release 目录，Windows 无配置包及 Linux amd64/arm64 包均为 0.1.14。停止进程后覆盖，16 个配置及身份数据文件哈希保持不变，并恢复原运行服务。使用实际证书验证协调服务的 HTTPS 更新清单、完整包下载和哈希；运行数据路径返回 404。服务端本机节点已与 10.77.0.14 恢复公网直连（约 8 ms），另外三台在线节点也显示公网直连；尚未代替用户验证各远端客户端相互之间的实际连接。

服务端与受影响客户端均应原地更新至 0.1.14，让后台进程加载修复；不需要退网、重新注册或删除配置。旧客户端进程中已经留存的永久关闭状态不能仅靠升级协调服务消除。

本次修复针对证书更新后的授权恢复。此前跨公网 UDP/QUIC 握手超时属于另一条故障路径，不能仅凭这些测试宣称所有公网直连问题均已解决。历史重复设备记录也不会自动合并。
