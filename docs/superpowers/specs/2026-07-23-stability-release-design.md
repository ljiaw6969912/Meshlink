# Meshlink 稳定修复版产品设计

- 日期：2026-07-23
- 状态：设计已确认，等待书面规格审阅
- 版本定位：下一稳定修复版

## 1. 背景

当前版本已经具备自建 Hub、加入网络、节点发现和远程桌面等基础能力，但产品状态与真实连接状态之间存在偏差：邀请码内容可能显示不全，退出网络不会彻底清理，Hub/Relay 会混入普通节点列表，Hub 断开后其他节点仍可能显示在线，官方 Hub 入口对用户可见但实际不可用。

这些问题会让用户无法判断网络是否真正可用。下一版本先完成稳定性收敛，建立可信的状态和操作语义，再单独推进 P2P 数据面与官方 Relay 商业化。

## 2. 产品目标

本版本应达成以下结果：

1. 用户看到的节点列表只包含可操作的真实设备。
2. 节点在线状态与当前可用连接一致，不显示过期在线状态。
3. “断开连接”和“退出网络”具有清晰且不同的结果。
4. 自动重连期间有准确反馈，重连成功后重新建立可信节点列表。
5. 正式版不暴露尚不可用的官方 Hub 功能。
6. 邀请信息和离线诊断等基础操作不再产生误导。

## 3. 范围

### 3.1 本版本包含

- 邀请码和邀请链接的完整显示、滚动与复制。
- 网络连接状态和节点在线状态的统一规则。
- Hub/Relay 等基础设施节点的列表过滤。
- Hub 断线、自动重连、手动重连和重连成功后的状态刷新。
- “断开连接”与“退出网络”的独立操作语义。
- 退出网络后的本机身份、加入信息和节点列表清理。
- 正式版隐藏官方 Hub，内部测试版按开关保留。
- 离线状态下的远程桌面诊断纠正。

### 3.2 本版本不包含

- P2P 打洞或点对点数据传输。
- 官方 Relay 数据面正式上线。
- 官方 Hub 账号、订阅、计费和付费能力。
- 对现有自建 Hub 转发架构的替换。
- 面向公网的正式商业服务发布。

## 4. 产品对象与显示规则

### 4.1 真实设备

真实设备是用户可以远程连接、远程桌面或管理的终端。只有真实设备可以进入普通节点列表和设备数量统计。

### 4.2 基础设施节点

Hub、Relay、控制服务器等只负责网络协调或数据转发，属于基础设施节点：

- 不进入普通节点列表。
- 不计入普通设备数量。
- 不提供远程桌面等设备操作入口。
- 可在内部诊断信息中出现，但不得改变普通用户的设备视图。

基础设施节点必须依据明确的节点角色进行识别，不能依赖名称、地址或展示文本猜测。

## 5. 状态模型

### 5.1 网络状态

产品统一使用以下网络状态：

| 状态 | 含义 | 节点列表行为 |
|---|---|---|
| 未加入 | 本机没有有效网络身份或加入信息 | 列表为空 |
| 已断开 | 身份仍保留，但当前没有连接 | 保留真实设备记录，全部显示离线 |
| 连接中 | 用户正在首次建立连接 | 不显示未经确认的在线状态 |
| 重连中 | 已有连接异常中断，正在自动恢复 | 保留真实设备记录，全部显示离线 |
| 已连接 | 当前连接正常，节点状态已经同步 | 按最新可信状态显示在线或离线 |

界面不得从缓存节点记录自行推断“在线”。只有当前有效连接提供的最新状态可以使节点显示在线。

### 5.2 Hub 断线

当前版本的所有节点通信依赖 Hub。客户端检测到 Hub 连接断开后：

1. 网络状态立即进入“重连中”。
2. 所有依赖该连接的节点立即显示“离线”。
3. 旧节点记录可以保留用于识别设备，但不能继续显示在线。
4. 自动重连在后台继续，不阻塞界面操作。

如果用户在重连期间选择“断开连接”，自动重连停止，网络状态进入“已断开”。如果用户选择“退出网络”，执行退出网络流程。

### 5.3 重连成功

重连成功不直接恢复旧在线状态。产品必须重新获取完整节点状态，并用新的可信快照替换旧状态：

- 最新确认在线的真实设备显示在线。
- 最新完整成员快照中的离线设备显示离线；未出现在该快照中的旧设备从当前节点列表移除。
- Hub/Relay 在进入界面前完成过滤。
- 网络状态在节点同步完成后进入“已连接”。

自动重连失败时继续显示“重连中”，并提供手动“重新连接”操作。错误提示应说明当前无法连接，不得暗示远端设备仍然可用。

## 6. 用户操作

### 6.1 断开连接

“断开连接”是可恢复操作：

- 停止当前连接和自动重连。
- 保留本机网络身份、加入信息和已知真实设备记录。
- 所有节点显示离线。
- 用户可以通过“重新连接”恢复连接，无需再次使用邀请码。

### 6.2 退出网络

“退出网络”是清除本机网络成员身份的操作，必须二次确认。确认信息应明确说明：退出后需要重新使用邀请码才能加入。

退出成功后必须同时满足：

- 停止当前连接及自动重连。
- 删除本机网络身份和加入信息。
- 清空节点列表和当前网络选择。
- 返回“未加入”状态。
- 应用重启后仍保持“未加入”，不得自动恢复旧网络。

退出操作应作为一个完整结果呈现。若本地清理未完成，界面必须提示退出失败，不能显示已经退出，也不能留下部分旧节点继续显示在线。

## 7. 界面设计

### 7.1 邀请信息

- 邀请码/邀请链接区域使用稳定高度。
- 长内容自动换行并支持垂直滚动。
- 一键复制始终可用，复制结果必须是完整原文。
- 内容变化不能挤压或遮挡相邻操作。

### 7.2 连接操作

- “断开连接”和“退出网络”作为两个独立操作显示。
- “退出网络”必须有二次确认。
- “重连中”期间显示明确状态，并提供手动“重新连接”。
- 状态变化后界面主动刷新，不要求用户手动刷新节点列表。

### 7.3 官方 Hub

- 正式版完全隐藏官方 Hub 入口和相关不可用功能。
- 内部测试版可通过明确的测试开关显示入口。
- 在账号、持久化、真实数据链路、订阅计费和服务保障未完成前，不得将官方 Hub 描述为可用服务。

## 8. 远程桌面诊断

诊断流程必须先判断本机网络和目标节点状态：

- 网络未连接时，直接返回“网络未连接”。
- 目标节点离线时，直接返回“目标设备离线”。
- 只有网络已连接且目标节点在线时，才继续检测远程桌面端口。
- 前置状态不满足时，不得因系统路由或偶然端口响应给出“可用”结论。

## 9. 验收标准

| 编号 | 验收场景 | 通过标准 |
|---|---|---|
| AC-01 | 邀请链接超过显示区域 | 可以滚动查看完整内容；复制结果与原文完全一致 |
| AC-02 | 成功加入含 Hub 和多个终端的网络 | 列表和设备数量只包含真实终端，不包含 Hub/Relay |
| AC-03 | Hub 连接中断 | 断线被检测后，网络进入“重连中”，所有相关节点显示离线 |
| AC-04 | 自动重连成功 | 重新获取节点状态；仅最新确认可用的真实设备显示在线 |
| AC-05 | 自动重连失败 | 保持准确的重连状态，节点不恢复虚假在线，并可手动重连 |
| AC-06 | 用户选择断开连接 | 身份和设备记录保留，节点全部离线，可直接重新连接 |
| AC-07 | 用户确认退出网络 | 节点立即清空；重启应用后仍为未加入状态；重新加入需要邀请码 |
| AC-08 | 用户取消退出网络 | 当前连接、身份和节点状态不发生变化 |
| AC-09 | 打开正式版设置 | 官方 Hub 入口不可见 |
| AC-10 | 打开内部测试版并启用测试开关 | 官方 Hub 测试入口可见，且明确标识为测试能力 |
| AC-11 | 网络未连接时启动远程桌面诊断 | 返回网络未连接，不继续给出远端端口可用结论 |
| AC-12 | 状态发生变化 | 界面自动反映最新状态，无需手动刷新 |

## 10. 验收证据

版本交付时至少需要提供：

- 邀请信息长文本显示和复制结果的验证记录。
- Hub/Relay 过滤与设备数量一致性的验证记录。
- Hub 断线、自动重连成功、自动重连失败和手动重连的状态验证记录。
- 断开连接与退出网络在应用重启前后的验证记录。
- 正式版与内部测试版官方 Hub 入口差异的验证记录。
- 网络离线和目标设备离线两类远程桌面诊断验证记录。
- 相关自动化测试通过结果，以及真实 Windows 桌面端的人工验收记录。

## 11. 已知风险

- 本版本仍使用 Hub 转发数据，服务器带宽压力和单点依赖不会得到解决。
- 实际断线发现速度受连接保活和超时机制影响；验收以客户端确认断线后的状态切换为准。
- 若旧数据来源没有明确节点角色，需要在交付前完成兼容识别，否则可能继续混入基础设施节点。
- 退出网络涉及身份和配置清理，必须验证异常中断及应用重启场景，防止出现部分清理状态。

## 12. 后续阶段

稳定修复版验收完成后，再启动独立的 P2P 数据面项目：Hub 只负责身份、发现、授权和短暂握手，设备优先点对点传输，无法直连时再按明确策略使用 Relay。官方 Relay、合规责任和收费模式应在该项目中单独设计与验收。
